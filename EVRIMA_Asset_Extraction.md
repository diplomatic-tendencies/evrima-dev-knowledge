# EVRIMA asset extraction (CUE4Parse + Oodle)

This is the working pipeline for extracting game assets (meshes, textures, animations, sound) from EVRIMA's .pak archives. The pipeline is headless (no Unreal Editor required) and produces standard formats (glTF, PNG, WAV).

Asset extraction is useful for:

- Reading mesh data to understand species' weight scales, attack hitboxes, and visual reference.
- Inspecting customizer-default colors per species.
- Building a custom asset pack (`.pak` content) that references the same materials and textures the base game uses.
- Producing reference imagery for documentation and write-ups.

## Toolchain

- **CUE4Parse**: a .NET library for reading UE .pak archives. Open source.
- **Oodle**: the compression library UE uses for .pak content. Required because EVRIMA's .pak files use Oodle compression.
- **A `.usmap` file**: a serialized type-info dump that CUE4Parse uses to interpret the binary .pak contents. Auto-generated by a UE4SS dump command on the running game.
- **The .pak AES key**: required to decrypt EVRIMA's encrypted .pak chunks. Distributed via a separate channel; redacted from this document.

## Setup notes

Use the master branch of CUE4Parse, NOT the NuGet release. The NuGet release lags behind master by several months and is missing fixes for newer .utoc format versions. EVRIMA's .pak files use `.utoc v8` which requires the post-NuGet fixes.

Clone CUE4Parse, build it locally with `dotnet build`, and reference the built DLLs from your extraction script.

Oodle is not redistributable. The standard procedure is to copy `oo2core_X_win64.dll` from a UE source install (or from the game's own binaries directory if it ships one) into your extraction tool's working directory.

The `.usmap` file is generated by running a UE4SS dump command on the running game. The dump produces a serialized type-info file that captures the current build's UCLASS, UFUNCTION, and UPROPERTY definitions. Without an up-to-date `.usmap` matching the current game version, CUE4Parse will fail to interpret struct contents.

## Mount order

CUE4Parse mounts .pak files in a specific order. The order matters because newer pak files override entries from older ones (the standard UE patching model). EVRIMA's pak directory typically contains:

- `pakchunk0-WindowsClient.pak` (base content)
- `pakchunk0-WindowsClient_P.pak` (first patch)
- `pakchunk0-WindowsClient_P2.pak` (second patch)
- etc.

The `_P`, `_P2`, etc. suffixes are patch generation. Mount in numerical order: `_P` first, then `_P2`, then `_P3`. This produces the same content the running game sees.

If you mount in the wrong order, you'll get old asset versions in places where newer patches replaced them. The symptom is "this asset looks wrong; it doesn't match what's in the game."

## Mesh export type dispatch

For mesh extraction specifically, the export path differs by mesh type:

- `UStaticMesh`: use the static-mesh exporter, produces a single mesh with materials.
- `USkeletalMesh`: use the skeletal-mesh exporter, produces mesh plus skeleton plus skin weights.
- `UAnimSequence`: use the anim exporter, produces a clip in the requested format.

The dispatch is `if mesh.GetType() == "USkeletalMesh" then exportSkeletal() else exportStatic()`. Getting this wrong (e.g. trying to export a USkeletalMesh as a static mesh) produces broken output or an exception.

The output format that's worked reliably across the pipeline is glTF. Both static and skeletal meshes export cleanly to glTF with materials and textures. Other tools (Blender, 3ds Max, custom engines) all consume glTF without issue.

## Verified extractions

Several species have been extracted end-to-end and validated:

- Pteranodon: full mesh, skeleton, default colors. Matches in-game appearance.
- Tyrannosaurus: full mesh, skeleton, default colors.
- Triceratops (cut content): full mesh, skeleton, default colors. Renders correctly when loaded into Blender.

The patterns generalize. Any species in the UHT dump under `/Game/TheIsle/Core/Characters/Dinosaurs/` can be extracted with the same procedure.

## Extraction script structure

```
1. Initialize CUE4Parse with:
   - Game version (UE 5.6 specific)
   - AES key (redacted; obtained separately)
   - Path to .usmap file
   - Mount paths (the pak files in correct order)

2. For each target asset path:
   a. Load the asset from the virtual filesystem
   b. Dispatch on type (UStaticMesh, USkeletalMesh, UTexture2D, USoundWave)
   c. Export to the appropriate output format
   d. Write to disk under <output-dir>/<asset-path>.<ext>

3. For texture-bearing meshes, also extract referenced textures
   into the same output tree.
```

The full script is 200-300 lines of C# depending on how much error handling and progress reporting you add. The CUE4Parse repo includes sample code for the basic load-and-export flow.

## What doesn't work

A few patterns that look obvious but fail:

**Direct file reads from inside .pak files.** The pak format is a custom archive with chunked compression. You cannot just open the .pak file as a zip; you need CUE4Parse (or a comparable library) to parse the index and decompress chunks.

**Hardcoded AES keys.** The AES key for EVRIMA's pak files is part of the redistribution restrictions on game content. Keys change with major game versions. If your extraction fails with "decrypt failed," your key is probably outdated; obtain the current key from the same channel that provided the original.

**Mixing Unreal Editor extraction with CUE4Parse.** The two tools use slightly different naming conventions for asset paths. If you extract via Unreal Editor and try to reference the same paths from CUE4Parse code, the lookups may fail. Pick one tool and stay with it.

**Extracting locked content.** Some assets are marked with a flag that prevents extraction even with a valid AES key. These are typically content the developers explicitly want unextractable (some pre-launch content, certain commercial-license assets). CUE4Parse will silently skip these or log a warning; the output asset count will be less than the input asset count.

## Use case: customizer default colors

Reading the default `FCustomizerDataBase` for each species. The CustomizerDataBase struct has 7 FLinearColor fields plus pattern info. Pulling the species' default values lets you display "this is what the species looks like in the box" reference imagery.

The procedure:

1. Mount the paks.
2. Load the species' BP_<Species>.uasset.
3. Read the CDO (Class Default Object) of the loaded class.
4. Read the CustomizerDataBase field on the CDO.
5. Extract each color value plus pattern index.

This produces a per-species table of default colors that matches the in-game customizer's initial state.

## Use case: weight extraction for KillFeed payout

Reading the weight curve per species. Weight is a function of growth percentage; the exact curve varies by species and is stored in a data table referenced by the species BP.

The procedure:

1. Load the species' BP.
2. Find the WeightCurve property (or equivalent; the exact name varies by species).
3. Extract the curve points.
4. Sample at growth values 0.0 through 1.0 to produce a per-species weight table.

This is useful for the bot side of a kill-feed integration. The bot can compute payout from the kill event's `victim_weight_kg` field, but knowing the full curve lets the bot show "this kill was X% of an adult Tyrannosaurus" style breakdowns.

## Closing notes

The extraction pipeline took a few iterations to get right, mostly around mount order and the NuGet-vs-master CUE4Parse issue. Once the toolchain is set up, extraction is fast (an entire dino species mesh plus textures in under 5 seconds).

For ongoing use, build a small wrapper script that takes "species name" as input and outputs the standard set (mesh as glTF, all textures as PNG, default colors as JSON). One script invocation per species means low friction for "I need to look at the Allosaurus model" style ad-hoc work.

Refer to `EVRIMA_Lua_Safety_Rules.md` for the constraint that FString fields on UE structs cannot be safely read or written from Lua. This applies to in-game struct access, NOT to offline asset extraction. CUE4Parse reads asset files; it does not interact with the running game.
